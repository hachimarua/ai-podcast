## 今回の改善目的

- 5分に収めるため、AIニュースの説明が一言だけになる問題を減らす。
- 「プロンプトを書きましょう」など、既に実践済みの初心者向けTipsを減らす。
- 「知らなかった」「実際に試した」と感じられる実践者向け内容へ引き上げる。
- この仕組みを、将来の臨床知識・抄読会ポッドキャストにも展開できるプロトタイプにする。

## 現時点で合意に近い方向性

- 配信は1日1本を維持する。
- 通常は `Daily Brief` 4〜6分とする。
- 週1回、通常回と置き換えて `AI実装ラボ` 8〜12分を試す。設定上の初期曜日は日曜日だが、自動切替は無効のままにする。
- Dailyは主ニュース1件を深掘りし、Tipsは価値がある場合だけ採用する。
- Labは1テーマを複数ソースで確認し、具体的手順、期待結果、適用しない条件まで扱う。
- 番組用編集プロフィールは、共有記憶層から公開可能な項目だけをホワイトリスト方式で抽出する。
- 編集QAの初期導入はシャドー評価とし、それだけで公開を止めない。

## 監査・役割分担

- GitHub Actions: 毎朝の生成・公開と決定論的チェック。
- 軽量モデル: 新規性、密度、実践性、根拠、非重複性のシャドー監査。
- Sidecar: 1日1回、未処理の改善Proposalだけを確認する。
- Gemini / Antigravity: 日常的な小修正、検証、commit・pushの主担当。
- Codex: 毎日の監査には常駐しない。公開・個人情報境界、Workflow、権限、Secrets、依存関係などの高リスク変更と節目レビューを担当する。
- ユーザー: 新規性と実践価値の最終評価。

Codexの節目レビュー候補は、番組用プロフィール初回承認、AI実装ラボ公開前、2週間パイロット後。

## Apple Watchフィードバック案

文字盤には新しいComplicationやボタンを追加しない。既に利用している長押しSiriから音声ショートカットを起動する。

暫定案:

- 「AIラジオ 初耳」
- 「AIラジオ 知ってた」
- 「AIラジオ 試した」

記録する最小項目は `episode_id`、`reaction`、時刻。メール、自由記述、毎日の回答要求は設けない。無入力は低評価と推定せず、評価データ不足として扱う。

Apple公式ではショートカット名をSiriへ言って起動する。一言一句の一致は明記されていないが同義語も保証されないため、固定名3本で実機試験し、失敗が確認された語だけ別名入口を追加する。

## まだ議論が必要な点

### 1. 番組構成

- Labは週1回、通常回と置き換えて2週間試す方向でユーザー合意済み。
- Dailyは主ニュース1件、関連する場合だけ2件目、復習項目最大1件、Tips任意として実装済み。
- Labは同一テーマ、異なるURL・配信元2件以上、信頼済み公式ソース1件以上、復習項目最大1件として実装済み。
- 実施曜日と8〜12分の最終的な妥当性は、Phase 10の合格音声2本をユーザーが試聴してから決める。

### 2. フィードバック入力

- 3つの音声ショートカットへ分ける推奨案でユーザー合意済み。
- `初耳` を当日最新回へ自動対応させる。
- 数日後の `試した` を、直近で `初耳` と記録した項目へ対応させてよいか。
- 受付データをどこへ保存するか。既存クラウド環境を再利用する場合も、凪のUIやデータとは分離するか。
- 反応入力そのものが新しい負担にならないか。実入力なしの短期試験が必要か。

### 3. 評価指標

- 「知らなかった 週3回」「試した 週1回」を、2週間パイロットの観察指標として使うか。
- 入力件数が少ない場合に、番組品質と入力導線の問題をどう切り分けるか。
- `known`（音声名は `知ってた`）をTipsの重複・初歩化判定へどう反映するか。

### 4. 共有記憶層強化（このプロジェクトから分離済み）

- 図解台帳、アーキテクチャ、ロードマップの横断管理は別プロジェクト・別チャットで扱う。
- AIニュース側には各プロジェクトの横断台帳を実装しない。
- このリポジトリでは `docs/README.md` と `docs/visuals/` を正本として維持する。

### 5. 外部事例の確認

- 2026-07-14に公式・一次資料中心の限定調査を実施した。
- Daily 4〜6分、週1 Lab 8〜12分、Siri 3反応は現案維持でよい。
- 編集QAは、固有名詞・日付・数値・機能可否・引用・URLの公開前ゲートと、新規性・密度・自然さ等のシャドー評価へ二層化する。
- 2週間パイロットでは、取得可能な場合だけ30秒到達・最終区間到達を補助指標にする。Apple Podcasts Analyticsはリスナー数条件があるため主指標にしない。
