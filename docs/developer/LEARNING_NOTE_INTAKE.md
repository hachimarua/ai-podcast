# 学習ノート取り込み（AIチャット → Obsidian → Notion → 放送）

AIチャットで調べた内容を、手作業の転記なしで放送候補にするための取り決め。
Gemini のカスタム Gem が主経路だが、Codex など他のチャットからの貼り付けも受け取る。

## 経路

```
AIチャットの回答（保存用ブロック / ただの本文）
  → ⌥⌘L / scripts/save_learning_note.py
  → MainVault/20_Dev_開発/Learning/YYYY-MM-DD_用語.md（ai_radio: true）
  → obsidian_inbox_adapter.py → Notion 受信箱
  → process_inbox.py → Notion 学習データベース
  → 毎朝4:00の放送候補
```

## 受け口は広く、選別は処理側で（2026-08-01 変更）

当初は `# 用語名` で始まらないクリップボードを保存段階で拒否していた。関係のないメモが
流れ込むのを防ぐためだったが、Gem 以外のチャット（Codex のサイドチャットなど）の回答は
素のテキストなので、良い内容ほど弾かれるという逆転が起きた。

そこで判断の位置を変えた。**保存はほぼ通し、要否は本文が全部そろう処理段階で決める。**

- 保存段階（`save_learning_note.py`）で断るのは、空とサイズ超過だけ
- 学習素材かどうかは `process_inbox.py` が Gemini の `is_learning_material` で判定する
- 判定は門戸を広く取り、日記・予定・買い物メモなど明らかに無関係なものだけ落とす
- 落としたものは削除せず受信箱に残す。誤判定でも Notion 受信箱を見れば残っている

## 形式をそろえる理由

以前は Gem の表（テーブル）を人が Notion 受信箱へ貼り、`process_inbox.py` が
Geminiで用語名を推測していた。

`No content found` や `情報なし` が学習項目として登録されていた原因は、
**本文が空の受信箱ページ**である。旧実装は本文が空のときタイトルだけを
Geminiへ渡していたため、中身のないページからAIが項目をでっち上げていた。
あわせて、`fetch_page_content`が読むブロック種別に`table`が入っておらず、
表として貼り付けた内容は読まれずに落ちていた。

そこで **保存する時点で最終形式にする** ことにした。Obsidianから昇格したノートは
`process_inbox.py` がAIを通さず決定論的に登録する（設計原則2「まず決定論、必要な箇所だけAI」）。

## 保存用ブロックの形式

先頭行が `# 用語名` なら、それがそのまま学習データベースの「名前」になり、本文はAIを
通さず登録される。**この形が最短経路**なので Gem 側はこの形式を維持する。表は使わない。

先頭に `# ` が無い貼り付けも保存できる。その場合は仮の題（1行目の冒頭40字まで）で
ファイル名を付け、`format: raw` を立てて、用語名と要約は受信箱側でAIが付ける。

```markdown
# CQRS Read Model

## ひとことで言うと
更新用（Write）と参照用（Read）のモデルを完全に分けて設計する手法。

## 噛み砕いた解説
- Write Model は整合性を最優先し、正規化して保存する。
- Read Model は表示速度を最優先し、非正規化して保持する。

## 医療現場での例え
- Write Model は主訴・経過・処方を詳細に書く本カルテ。
- Read Model は外来受付で一目で見る退院サマリーや受付一覧。

## なぜ使うのか
- 目的: 読み出しのレスポンスを上げ、書き込み側と干渉させないため。
- 理由: 閲覧回数が記入回数より圧倒的に多いシステムで効果が大きい。
- 代替案: 単一モデル（CRUD）、キャッシュ（Redis）。

## 関連用語
- Write Model: 整合性を保ちながら安全に更新・保存するためのモデル。
- 結果整合性: 書き込み直後は反映に僅かなタイムラグがある状態。
```

## Gem 側の追加指示

カスタム Gem「プログラミング勉強 202605-」の指示へ次を追記する。

> 回答の最後に、必ず「保存用ブロック」を1つだけ出力する。
> 保存用ブロックは ```markdown のコードブロックで囲み、コピーしてそのまま
> 保存できる完成したノートにすること。
> - 1行目は必ず `# 用語名`（記号や番号を付けない）。
> - 見出しは `## ひとことで言うと` `## 噛み砕いた解説` `## 医療現場での例え`
>   `## なぜ使うのか` `## 関連用語` の順で使う。
> - 表（テーブル）は使わない。箇条書きで書く。
> - 「情報なし」「該当なし」しか書けない場合は、保存用ブロックを出力しない。
> - 患者個人を特定しうる情報は書かない。例えは一般的な診療の場面にとどめる。

本文側の解説（結論・噛み砕いた解説・ITパスポート知識との接続など）はこれまでどおりでよい。
保存用ブロックはその要約版として最後に付く。

## Mac 側のショートカット

1. ショートカット.app で新規ショートカットを作る。
2. アクション「シェルスクリプトを実行」を追加する。シェルは `/bin/zsh`、入力は「なし」。
3. スクリプト欄に次の1行を入れる（パスにスペースがあるので引用符ごと貼る）。

```bash
"/Users/sakiya/Documents/Antigravity 2.0/AI news knowledge learning system/venv/bin/python" "/Users/sakiya/Documents/Antigravity 2.0/AI news knowledge learning system/scripts/save_learning_note.py"
```

4. 名前を「学習ノートを保存」にする。
5. ショートカットの詳細でキーボードショートカット（例: `⌃⌥⌘L`）を割り当てる。

初回実行時に、Documentsフォルダへのアクセス許可をmacOSが1度だけ確認する。

使い方は、Gem の保存用ブロックの右上のコピーボタンを押してからキーを叩くだけ。
成功・失敗は通知センターに出る。

## scripts/save_learning_note.py の約束

- クリップボード（`--stdin` で標準入力）だけを読む。Vault内の他のファイルは読まない。
- **保存しないのは空と2万文字超だけ。** 見出しの有無では断らない。
- frontmatter の `format` が経路を決める。`structured`（先頭が `# 用語名`）/ `raw`（それ以外）。
- ファイル名は `YYYY-MM-DD_用語.md`。用語が無ければ1行目から作った仮の題を使う。
  同名があっても上書きせず `-2` を付ける。
- 保存後に `obsidian_inbox_adapter.py` を子プロセスで実行し、その日の4:00の放送に間に合わせる。
  取り込みに失敗しても保存済みノートは残り、Sidecarの毎日06:30で再取り込みされる。

## process_inbox.py の分岐

| 受信箱アイテムのタイトル | 処理 |
|---|---|
| `Obsidian｜用語｜source_key` | AIを通さず、用語と本文をそのまま学習DBへ登録 |
| `Obsidian未整形｜仮の題｜source_key` | Gemini で用語名と要約を付けてから登録 |
| それ以外（手入力のメモ） | 従来どおり Gemini で構造化 |

どの経路でも、次の場合は**登録せず受信箱に残す**。放送そのものは止めない。

- 本文が空（タイトルだけからAIに中身を書かせない）
- 用語または要約が `No content found` `情報なし` `該当なし` などのプレースホルダー
- Gemini が `is_learning_material: false` と判定（日記・予定・買い物メモなど）

臨床の記録もこの判定で落ちる想定だが、これは最後の網であって匿名化の代わりではない。
落ちるのはNotion受信箱へ入った後なので、患者情報を含むテキストは⌥⌘Lで送らない。

`fetch_page_content` は `table_row` と入れ子ブロックも読むため、表として貼り付けた
内容も落とさない。ログには受信箱内の位置だけを出し、タイトルや本文は出さない。
